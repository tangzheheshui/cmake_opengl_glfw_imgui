00先说清它是什么

不是通用引擎，是一个用来看模型的 CAD 风格演示：加载 duck.dae，架一个相机，带阴影、天空、剖切、线框、X-ray、鼠标点选高亮，还要在 OpenGL 和 Vulkan 上跑出同样的画面。整套代码的存在理由，就是把这套内容从 GL 搬到 Vulkan，且搬的过程中不能把画面弄坏。

所以判断这个架构好不好，标准不是「像不像商业引擎」，而是三条：迁一个特性会不会牵动全局、搬错了能不能当场发现、两端的画面能不能对上。 下面每一节都会落到其中一条上。

能力OpenGLVulkan证据（可自己去查）
模型legacy + RHI 两条路径强制 RHIRenderSettings::modelUseRHI；mesh_pass 里 useRHI = VK 或 开关
线条legacy + RHIRHIlineUseRHI，注释写明「已过逐像素等价性对比」
文字legacy 字形 + SDF 图集SDF 图集textUseRHI；main.cpp 里 legacyGlGlyphs = !useVulkan
阴影有没有res/shaders_vk 里没有 shadow 着色器；renderScenePasses 里 VK 直接跳过 CShadowPass
天空有有shaders_vk 有 vert_sky / frag_sky（且槽 3 约定给 cubemap）

这张表本身就是架构摘要 每一行的「GL 有 / VK 没有」都是文件层面能验证的事实。也正因为如此：要判断「阴影到底迁没迁」，看 res/shaders_vk 有没有 shadow 着色器，比看进度文档可信。 之前两份文档在这一点上互相矛盾，原因就是它们都没去数着色器文件。
01模块清单：目录即架构

四个源码层不是按文件类型分的，是按「谁能看见谁」分的。下面这张表是这个仓库全部的骨架，没有省略。

app/ 宿主层：唯一知道窗口、ImGui、原生句柄的地方 ├─ main.cpp 启动九步 + 主循环 + 环境变量映射 ├─ GlfwHost 窗口 / GL 上下文 / createDevice / ImGui 初始化与关闭 ├─ SceneDemo 摆场景：模型、多视口、相机、演示内容 └─ DebugPanel 读写 RenderSettings 的 ImGui 面板 src/render/ 编排层：知道「画什么」，不知道「怎么画」 ├─ RenderSystem 一帧编排者（单例门面）：init / renderFrame / shutdown / 拾取 / 验证设施 ├─ pass/ Shadow / Normal / Sky / Pick（+ IRenderPass 基类） ├─ model/ model / mesh / mesh_pass / aabb / model_data / PassColor / PassTexture / Utf8IOSystem ├─ object/ Line / Sky / Text / ImageRectangle ├─ camera/ camera / CameraController ├─ scene / FontManager / shader / image / BaseDraw / DrawUniforms / Light └─ RenderSettings.h 全部开关都在这里（UI 读、渲染消费） src/rhi/ 契约 + 两个实现：全仓库唯一出现 vk* / gl* 的地方 ├─ IRHIDevice / IRHICommandList 两个需要多态的接口 ├─ RhiTypes.h 6 个句柄 + 8 个 Desc + Backend / DeviceInfo ├─ RHIFactory 唯一设备创建入口 ├─ Result.h / FormatInfo 错误返回值 / 格式与字节数映射 ├─ vk/ 9 个模块（见第 05 节） ├─ gl/ GLDevice / GLCommandList / GLProgram └─ detail/ HandleTable / DeletionQueue / FrameUniformRing src/core/ 底座：log / math / fs / color / debug / taskQueue 3rdparty/ res/ tools/ glfw glad glm imgui assimp freetype stb / shaders shaders_vk model texture font / check_layers rhi_gate

依赖方向单向：app → render → rhi → core。src/render 里一旦出现 #include "app/GlfwHost.h"，构建直接失败——tools/check_layers.cmake 扫全仓库 #include，命中就 SEND_ERROR。

它同时检查四件事：src/rhi 不许 include render/app/GLFW/imgui；src/core 不许 include rhi/render/app；src/render 不许 include app/imgui/GLFW；engine 目标不许链接 glfw/imgui。最后一条最重要：链接一旦带上，include 检查就形同虚设。

例外清单的设计值得照抄 现在只有一条合法例外：rhi/gl/GLCommandList.cpp（DrawUniforms 的 ABI 残留，注明「随 V3-2 绑定层重做」）。规则可破，但要写进脚本、要注明清理归宿。这一步把「临时妥协」和「永久债务」区分开了。
02启动：main 里的九步

app/main.cpp 是唯一一条从头到尾的线。它只有一百来行，但每一步的顺序都有原因。

01
调试看 RHI_DEBUG_LOG：有则把 stdout 设成无缓冲，并装 installCrashBacktrace。先装，后面崩了才有栈。
02
选择读 RHI_BACKEND，只认 vulkan，其他一律当 OpenGL。引擎自己不读环境变量，这是宿主的活。
03
兜底若本二进制没编 Vulkan（ENGINE_HAS_VULKAN=0），打印提示并退回 GL。只有这一种回退，运行期失败不回退。
04
窗口host.createWindow(1600, 900, useVulkan)：建窗 + GL 上下文（GL 后端下 RHI 不建上下文，要求调用时已 current）。
05
设备host.createDevice → RHIFactory::createDevice：填 DeviceDesc（窗口、swapBuffers、后端）。失败返回空指针 + err，不抛异常。
06
引擎RenderSystem::init(InitDesc)：只给 device 指针、资源根、帧缓冲尺寸 + 窗口尺寸两套（拾取坐标换算要用）、然后 onWindowSizeChanged。
07
资源preloadTextures；LoadFont（legacyGlGlyphs = !useVulkan）；把 RHI_SMOKE / RHI_TEXQUAD / RHI_CLIP 映射进 settings()。
08
UIhost.initImGui(useVulkan)。必须在设备之后：Vulkan backend 要 instance / physicalDevice / device / queue 都已存在。
09
场景SceneDemo::buildScene，然后主循环：update → newFrameImGui → ImGui::NewFrame → DebugPanel::draw → renderFrame → glfwPollEvents。

关闭是反过来再收一遍，而且是契约：shutdownImGui → RenderSystem::shutdown → host.takeDevice().reset() → glfwTerminate。那个 takeDevice() 就是为了让「设备归谁销毁」在代码里看得见。RenderSystem 的注释写得很直白：单例静态析构发生在 main 返回之后，那时再释放依赖图形上下文的资源会崩。

主循环里还有三个「回归测试」的钩子，都挂在环境变量上：RHI_EXIT_AFTER（跑 N 帧退出，供 CI）、RHI_RESIZE_AT（指定帧改窗口尺寸，测交换链重建）、以及 useVulkan 这个 bool 从头传到底——它是唯一允许在 app 层出现的后端知识。

03一帧：四个 Pass，一条主命令列表

RenderSystem::init 里 m_vec_renderpass 按顺序塞了四个 Pass，renderScenePasses() 顺序遍历。没有 Render Graph，没有自动依赖分析——就是这四个，按这个顺序。

01
CShadowPass
从光源视角把场景画进深度图，供主 Pass 用。开关 drawShadowPass。VK 端跳过：renderScenePasses 里对 VK 直接 continue，dynamic_pointer_cast 到 CShadowPass 才拦。用 cast 而不是加一个 Pass 类型的枚举，是为了不动基类。
02
CNormalPass
主 Pass。模型、线条、文字在这里画；剖切、线框、X-ray、选中/悬停高亮都在这层生效。它是最重的一个。
03
CSkyPass
天空盒。开关 drawSkyPass。两端都有；注意 cubemap 固定走纹理槽 3。
04
CPickPass
只在请求拾取的那一帧把场景画成 ID 图到离屏目标。关掉 drawPickPass 后点选就失效，注释里直接写了这句。
// 示意：形状对，签名以代码为准
if (!dev->beginFrame()) return;       // 最小化 / 交换链重建 → 整帧跳过
for (pass : m_vec_renderpass) {      // 四个，按顺序
    cl = dev->createCommandList();   // 附加列表
    pass->draw(scene);                  // GL 立即执行；VK 录进 cl
}
overlayFn(cl);                         // ImGui 合成到主列表
dev->endFrame();                        // 提交（附加列表按创建顺序 → 主列表）
dev->present();                         // 呈现

两个后端共用这一段，renderFrame 里几乎没有后端分支（注释原话：「GL/VK 主循环零后端分支（ImGui backend 初始化除外）」）。真正分叉的只有两处，都在细节层：

overlay 的插入点，两端真的不一样 VK：在 render pass 内、场景之后（ImGui 用 dynamic rendering，附件格式由 NativeHandles::colorFormat/depthFormat 告诉它）。
GL：在默认帧缓冲、GL_FRAMEBUFFER_SRGB 关闭之后（否则颜色差一截）。

这条差异没法靠抽象抹平，只能写进契约——setOverlayRenderer 的注释里就是这么写的。
04契约层：两个接口，六个句柄，八个 Desc

这一层的设计目标只有一个：让 src/render 里一行后端代码都不出现。 IRHIDevice 的全部方法按用途分七组，看这张表就知道契约的边界画在哪。

组方法说明
身份与能力backend / info / capabilitiesDeviceCapabilities 是结构化能力表，调试面板、启动日志、上层路径选择共用；GL 端未实现时返回空表（0/false = 未知）
资源创建createBuffer / createTexture / createPipeline / createUniformBlock / createSampler / createRenderTarget前三个纯虚（必须有），后三个有默认实现（默认「不支持」）
资源销毁destroyBuffer / destroyTexture / destroyPipeline / destroyUniformBlock / destroySampler / destroyRenderTarget都走延迟回收，不是当场 delete
有效性alive(BufferHandle) / alive(TextureHandle) / …默认只查 id != 0；后端覆写后增加「id 在范围 + 槽存活 + gen 一致」三条件
数据更新updateBufferGL 是 glBufferSubData；VK 是 staging 拷贝或 HOST_VISIBLE 直写
帧循环beginFrame / endFrame / present / onResize / framebufferSize / waitIdlebeginFrame 返回 bool；present 独立；RHI 永不回查窗口系统（尺寸靠 framebufferSize()）
命令列表commandList() / createCommandList() / destroyCommandList()提交顺序固定「附加列表（按创建顺序）→ 主列表」，主列表负责 UI 收尾
逃生舱nativeHandles(NativeHandles&) / nativeBuffer / nativeTexture / nativeSampler / nativePipeline按类型拆开，避免 nativeHandle(RhiHandle) 的跨类型歧义；正式路径不许依赖
「默认实现 = 不支持」这个选择很关键 createSampler、createRenderTarget、readbackTexture 都有默认实现：返回空句柄 / false。

好处是能力可以一个一个接：GL 端还没做 B4 的时候，VK 端已经能建 RT 了，两边仍然能编译、能跑，只是 GL 拿到空句柄。这叫「只加不改」——契约每次扩展都不动已有后端。
代价是失败是静默的：谁忘了检查返回值，会拿到一个空句柄继续往下走，然后黑屏。所以凡是调用这类方法的地方都必须判空，这也是为什么 alive() 要单独存在。

句柄只有 {id, gen} 两个字段，派生六个强类型：BufferHandle / TextureHandle / UniformBlockHandle / PipelineHandle / SamplerHandle / RenderTargetHandle。它们是纯数据结构，没有方法——有方法的对象会被上层「顺手」调用，抽象立刻漏。有行为的只有 IRHIDevice 和 IRHICommandList 两个。

发现一处注释与实现不一致（不是 bug，是会误导人） IRHIDevice.h 的注释写着「句柄 id 不复用：销毁后槽位保留为失效」，但 HandleTable 已经有 _freeSlots，alloc 优先复用刚释放的槽，同时 gen 自增。

实现是对的（复用 + 代际校验是标准做法），注释是旧的。但这类不一致最坑接手的人：他会按注释去假设 id 单调递增，然后写出 id = size + 1 这种依赖。
05Vulkan 后端是怎么组织的：九个模块

VkDevice.cpp 有 96 KB，但真正「编排」的部分只占一部分——其余被拆成了下面九个模块。这个拆法本身就是架构。

模块管什么拆出去的理由
VkDeviceinit 顺序、帧循环、资源创建、submit / present、能力查询入口它只做「编排」，具体机制在下面八个里
VkCaps版本、扩展、队列族、limits 探测能力探测和初始化策略分开，便于面板展示和日志
VkSwapchain交换链、图像、视图、renderDone 信号量（按图像下标）重建逻辑与生命周期独立，避免和帧循环搅在一起
VkFrames帧级同步：in-flight fence + imageAvailable，默认 2 槽位「帧在飞」这件事只在一个小文件里说得清
VkDescriptors两个 setLayout、全局 pipelineLayout、纹理描述符池、帧 uniform 环描述符是最容易写错的部分，单独隔离
VkPipelines管线创建 / 缓存管线状态组合多，缓存策略独立演进
VkShaderReflect读 SPIR-V 反射信息（binding、push constant 等）参数对齐靠反射算，而不是靠人记
VkMemoryAllocator显存分配（按内存类型与对齐分块）不自己管内存，就得天天对着 VkDeviceMemory 猜
VkCommandList录制：dynamic rendering、绑定、draw、set 判重每条列表按槽位持有自己的命令缓冲（V3-6 起）

描述符是怎么排的，这是整个 VK 后端最需要理解的一张图：

位置内容什么时候写
set0帧 uniform 环：一次绘制数据一段，靠动态偏移取每帧 beginFrame 归零；每次绘制 allocDrawUniforms 追加一段，返回偏移；环满会扩容
set1 .. N每张纹理一个 set（写一次，之后只绑不更新）纹理创建时写 sampler + view；池不够就扩容
兜底白纹理 / 白 cubemap未绑定的槽、上传还没完成的纹理都绑它，槽 3 约定给 cubemap
共用一个全局 pipelineLayout（所有管线共用）init 时建；这就是为什么改槽位数会牵动管线
push constant128 字节小参数直传，不占描述符
三个「槽位数」别搞混，它们不一样 kMaxTexSlots = 8 是常量上限；VkDescriptors::_texSlotCount 是按设备上限裁过之后的实际可用值（注释里那句「桌面卡通常 32、Intel / MoltenVK 可能 8，按上限裁，不够时只减少槽位，不崩」）；frameSlotCount = 2 是帧在飞数量（两套 uniform 环 + 两套描述符集）。

GL 端有对应的耦合：纹理槽数不能超过 GL 纹理单元数量，所以这个值改动要同时看两边。

同步只有两处，但都很关键。 帧级：VkFrames 两个槽位，每槽一个 fence + 一个 imageAvailable；第 N 帧等第 N-2 帧的 fence 完成，所以 GPU 在跑时 CPU 已经在录下一帧。首帧的 fence 预置成已信号，否则第一帧就会卡在等待上。图像级：renderDone 信号量按交换链图像下标分配，不是按帧——这是躲 VUID 00067 的标准做法。资源级：DeletionQueue::kLagFrames = 2，且 flush 必须在 fence 之后、帧号自增之前。

「驱动 API」那一层，我们有代码吗？ 几乎没有。 这一层属于 SDK，不属于我们——我们做的是按正确顺序调用它，不是实现它。硬要说「我们写的」，只有三样：

① 函数指针表。 instance / device 级 vkGet*ProcAddr 取地址。因为像 vkCmdBeginRenderingKHR 这种扩展函数，header 里只有声明，不取地址就是空指针——代码里因此存了 PFN_vkCmdBeginRenderingKHR，用之前还检查是否解析成功，失败就报错。
② 着色器编译。 GLSL → SPIR-V 在构建期由 glslangValidator 完成，缺了直接 configure 失败。
③ 同步与生命周期策略。 什么时候等 fence、什么时候 reset、删一个资源要等几帧——这属于「调度」，是真正的设计工作。

结论：越往下，代码越少、责任越大。 L5 近似零行，L6（同步）反而是最费脑子的那一层。
06迁移的真实形态：不是两套代码，是一排开关

这是这个项目最值得说的架构特征。它没有「GL 分支 / VK 分支」，而是每个绘制对象自己决定走哪条路径，由 RenderSettings 里几个 bool 控制。

开关管什么状态
lineUseRHI线条走 RHI 还是 legacy GLM2，注释写明已过逐像素等价对比
modelUseRHI模型走 RHI 还是 legacy GLM4.2，GL 下可切换做 A/B
textUseRHI文字走 SDF 图集还是 legacy 字形D4，两端都已走 SDF

落到代码里是同一个句式，在 mesh_pass、Line、Text 里反复出现：

// 形状一致：VK 上无路可退，必须是 RHI；GL 上由开关决定
bool useRHI = device && (device->backend() == rhi::Backend::Vulkan
                          || settings.modelUseRHI);
if (useRHI) {  // RHI：句柄 + 命令列表 }
else        {  // legacy：直接调 GL }

好处很具体：可以同帧比对。 selfTestAB（M4.2 验证设施）就干这个——同一帧两条路径各画一次，逐像素比。这比「截图看一眼差不多」强一个量级，也比「迁完再说」安全一个量级。它把「两套路径并存」从风险变成了可测量。

代价必须说清 每个绘制对象两条路径，代码量翻倍，而且过期开关会变成谎话：一条没人跑的 legacy 路径就是死代码，但布尔值看起来还很正经，后来的人会以为它还在用。

纪律只有一条：迁完就删开关和 legacy 路径，别留着当安全绳。按这个标准，textUseRHI 已经两头同向了，可以埋；modelUseRHI 在 GL 上还有对比价值，先留。
07鼠标点一下，背后发生了什么

这是全仓库最完整的一条链路，跨了 app、render、rhi、驱动四层。它的形状是被物理事实逼出来的：屏幕上的像素在 GPU 上，CPU 不能当场问「这里是什么」。

N
app左键抬起 → RenderSystem::onMouseLeftUp → requestPick(x, y)。只记坐标，不做事。
N
renderm_pickReq.pending = true；坐标从窗口坐标换算到帧缓冲像素。窗口尺寸与帧缓冲尺寸不同时这一步不能省，这就是 InitDesc 要传两套尺寸的原因。
N
renderCPickPass 把场景画进 m_pickRT，每个物体涂成自己的 ID 颜色。看着是画面，实际是数据。
N+1
rhi回读那 1 个像素。必须等下一帧：这一帧的提交还没完成，现在读会读到上一帧内容。
N+1
render解码 ID → 写 settings.selectedId（0 = 没选中，BaseDraw::GetID）。
N+2
render主 Pass 里那个物体被淡蓝高亮，强度 highlightStrength；悬停走 hoverId + hoverStrength。

悬停是同一套再加两层节流：位移阈值（m_hoverLastX/Y）和冷却帧数（m_hoverCooldown）。不节流的话，鼠标每动一像素就要画整张 ID 图——注释里也写了「避免每次 mousemove 都渲染整幅 ID 图」。

这条链路说明两件事 一、回读是架构级成本：任何「点一下看结果」的功能，天然带一到两帧延迟，UI 不能同步等。
二、这只是「ID 图拾取」，不是 GPU 查询。以后要做大规模拾取，这条撑不住，得先用 aabb 在 CPU 上做射线求交预筛——包围盒已经在 mesh 里存着，只是现在没接这条路。
08一个模型是怎么进到显存的

从 res/model/duck.dae 到屏幕上的一只鸭子，中间四个文件分工明确。

文件管什么为什么单独存在
model.cppAssimp 读文件 → 节点树 / 网格 / 材质 / 动画格式转换与场景图，跟 GPU 无关
model_data.h中间数据（顶点、索引、材质参数）把「Assimp 的结构」和「引擎的结构」隔开
mesh.cpp网格 + aabb 包围盒包围盒给 frustumCull 用（模型级保守剔除，像素不变，只省 draw）
mesh_pass.cpp把网格真正画出去，两条路径它就是 modelUseRHI 分支所在地

材质走 PassColor / PassTexture（两个正交的绘制变体），贴图走 image.cpp（stb_image）→ RHI createTexture。PassColor 和 PassTexture 分开，是为了让「纯色 / 贴图」不必在 shader 里做分支——着色器变体比运行期分支便宜。

Utf8IOSystem 很不起眼但很关键：Windows 上路径是 GBK，Assimp 要 UTF-8。「中文目录下的模型读不进来」，九成是这里，而不是加载代码。

一处迁移期典型写法，收尾时要清 model.cpp 里有一处判断是「backend != Vulkan 才做某段后处理」。这类「先假定是 GL、再补 VK 特例」的写法不会报错，但会让两端行为悄悄不同。收尾时应该反过来写成「默认正确 + 例外显式」，否则半年后没人知道哪条是基准。
09两个后端，真实差在这六处

除这六条，其他都应该由契约吸收掉。差在这六条之外，就说明抽象没写到位。

1
overlay 插入点。 VK 在 render pass 内、场景之后；GL 在默认帧缓冲、关掉 GL_FRAMEBUFFER_SRGB 之后。ImGui 的 GL backend 会改全局状态。
2
回读行序。 RenderSystem 里有一行 row = VK ? (127 - cy) : cy。Vulkan 图像原点在上方，回读是倒的。PPM 导出、拾取、A/B 对比都会撞上。
3
视口 y 轴。 同样的翻转还出现在视口与拾取坐标，所以这类换算集中写、不要散落——散落就是逐个漏。
4
状态是否全局。 GL 有 GLStateSnapshot（深度、深度写、混合、剔除、FBO、视口、裁剪、多边形模式、线偏移），进 Pass 存、出 Pass 还原；VK 没有全局状态。
5
绑定时机。 GL bindTexture 立刻生效；VK 只记「set1 的第 slot 个是哪张图」，到 draw 才 vkCmdBindDescriptorSets，连续相同就跳过。
6
命令何时执行。 GL 的 createCommandList() 返回主列表本身，调用即刻生效；VK 录完才在 endFrame 提交。

第 6 条是唯一一条会悄悄出错的：GL 上如果你录的顺序和提交顺序不一致，画面错乱但不报错。这条已经在契约里写清了——IRHIDevice.h 里「硬约束一：录制顺序必须等于提交顺序」和「硬约束二：多线程并行录制只对 Vulkan 成立」，docs/4-RHI接口契约.md 也有对应的一节。这部分是补齐了的，不用再动。

另外顺带一条不算差异、但常被误认为差异的：Vulkan 的深度范围是 0..1，GL 是 -1..1；Vulkan 的 y 朝下，GL 朝上。投影矩阵要按后端选，这不是 bug，是两套裁剪空间定义。

10验证设施，也是架构的一部分

这个仓库有个不常见的优点：它把「怎么证明自己对」写进了运行时代码，不是只写在文档里。全部挂在环境变量上，不影响正常跑。

开关 / 设施验证什么性质
RHI_SMOKE最小三角形：RHI 链路通不通永久
RHI_TEXQUAD贴图四边形：纹理 + 描述符链路永久
RHI_RT_TEST离屏 RT + 回读中心/角落像素，两阶段状态机永久（B4）
RHI_PICK_TEST启动后自动在屏幕中心拾取一次永久（D2）
RHI_CHURNN 轮建/删纹理，压延迟销毁队列永久（V3-0）
RHI_VK_VALIDATION验证层开关（1 强制开 / 0 强制关，Debug 默认开）永久（A1）
RHI_PROBE第 30 帧回读屏幕中心注释自述「M3 验证用，之后可移除」
RHI_DUMP导出整帧 PPM注释写明「正式调试设施」
selfTestAB同帧两条路径各画一次，逐像素比M4.2，迁移期最有价值的一个
RHI_VIEWPORTS多视口划分门禁里跑 4 视口
RHI_RESIZE_AT指定帧改窗口尺寸，测交换链重建永久

门禁脚本 tools/rhi_gate.sh 把它们串成 9 次运行 + 一次分层检查：GL 四跑、VK 五跑。VK 侧标准比 GL 严一档——验证层出现 error 即失败，WARN 不拦。 这个不对称是有意的：VK 的错误最容易被「画面看着还行」掩盖。

脚本里还有一处真踩过的坑：macOS 上必须把 DYLD_LIBRARY_PATH 显式传给 env，因为部分环境（沙箱 / 硬化运行时）会在 exec 时剥掉继承变量，MoltenVK 找不到 ICD，vkCreateInstance 直接返回 -6。这种坑不可能靠读文档预见，只能写进脚本。

11现在的真实边界，和下一步

按当前代码，不按计划。前几轮列过的六条里，四条已经关掉了。

事现状说明
命令列表泄漏已修destroyCommandList 已进接口：VK 覆写（主列表由设备持有，传主列表会告警忽略），GL 空实现；文档写明「附加列表必须显式配对销毁，不许每帧隐式累积」
framebufferId已删契约层不再有 GL 概念直通
纹理槽太少已修kMaxTexSlots 已是 8，实际可用数按设备上限裁
句柄 id 不回收已修HandleTable 有 _freeSlots，先出后进 + 代际自增（注释待更新，见第 04 节）
录制顺序契约已写IRHIDevice.h 两条硬约束 + docs/4-RHI接口契约.md 对应章节
VK 上的阴影没有不是「待迁」，是「还没写」：shaders_vk 无 shadow 着色器，CShadowPass 在 VK 下被跳过
MRT没有AttachmentLayout 是单数。做延迟渲染那天必须改成数组 + count，会牵动所有建管线的地方
VK 多视口未查清GL 靠 model_multiview.geom；shaders_vk 没有对应着色器。要么没做，要么用了别的路子——需要你确认
GL 真并行录制不可能永久约束，已写进硬约束二
legacy 路径该收摊开关与旧 GL 路径还并存，见第 06 节的纪律

下一步最该做的不是继续加特性，而是收摊：把已经两头同向的 textUseRHI 埋掉，把没人跑的 legacy 路径逐条删。迁移项目最常见的失败不是迁不动，是迁完一直不收摊，两套路径永远都在，最后谁也不敢删。

一个和代码无关、但必须先定的事 代码注释和 check_layers.cmake 引用 docs/ARCHITECTURE_INTERFACES.md（§2.1 / §3.1 / §4.5），还引用了 C1a C1b C5 A1 B1 D4 D5 D7 M3 V3-0 L0 L1 这批条款编号，但仓库里没有这个文件。

也就是说：最权威的那份架构文档现在不存在，规则只活在注释和这个 HTML 里。要么把这份改名为它，要么在文末附条款索引——建议后者，文件名保持 1-架构设计，把每个编号的意思固定下来。

三件「到那天一定逼你改结构」的事，现在不用做，但心里要有数：bindless（句柄从「一个资源一个 id」变成「一段 id」）、自动同步的 Render Graph（四个 Pass 的顺序和屏障从手写变成编译出来）、多线程录制（VK 可以，GL 不可能，这条永久留在契约上）。
