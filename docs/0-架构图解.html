是怎么到屏幕上的

中间隔了六层。这一份从最外面开始，一层一层往里剥：每层只接收一件事、只决定一件事、只往下交一件事。剥到最里面的时候，你就已经在写 vkCmdDrawIndexed 了。

00先看全景：六层，一根竖线

不要先看目录式的功能清单。先记住这个堆栈的形状——它决定了后面所有代码为什么长那样。

L1
宿主 · app/
我有一扇窗，一双手。我决定什么时候画下一帧。
交出：一个 device 指针 + 一个 overlay 回调
L2
编排 · src/render/
我决定这帧画几个 pass、每个 pass 画什么。
交出：一串绘制意图（目标+管线+流+纹理+矩阵）
L3
契约 · src/rhi/*.h
我只做翻译：物体 → 句柄，「画」→ 命令。
交出：6 个句柄 + 8 个 Desc + 15 条录制方法
L4
后端 · src/rhi/vk src/rhi/gl
我把参数翻成真实调用。一套接口，两套实现。
交出：vk* 或 gl* 函数调用
L5
驱动 API
我按你给的顺序执行。我不猜你的意图。
交出：GPU 命令流
L6
同步与显存
我只管谁还在用、什么时候能复用。
交出：一帧像素
贯穿全篇的一条线 每一层干的事都是同一件：收窄 + 翻译。上层给的是「意思」，下层收的是「参数」。所以判断分层对不对，只看一句：这一层能不能在不知道下一层存在的情况下把自己的活干完。能，就对了。

下面的顺序就是往下剥的顺序。每一节的标题都是一个「这一层在做什么」。你随时可以回来看这个堆栈——每节开头也有一排小方块告诉你现在在第几层。

L1宿主层：我有一扇窗，一双手
宿主编排契约后端驱动同步

你按下运行，第一个跑起来的是 app/main.cpp。它干的事非常朴素：解析环境变量，建窗口，拿一只手，然后进死循环。

输入
操作系统给的窗口、鼠标键盘、一个 surface（在 Windows 上就是 HWND 背后那块可绘制区域）。
决定
什么时候开始新的一帧（每圈循环调一次 RenderSystem::renderFrame()）；这一帧要不要画（窗口最小化就整帧跳过）。
输出
把 IRHIDevice 指针和场景数据交给编排层，再挂一个 overlay 回调让 UI 能在同一帧里画。
这一层不懂
顶点怎么排、矩阵怎么算、有没有阴影。它连「三角形」这个词都不该出现。

看 GlfwHost 就知道这一层的边界感：它只做窗口、事件、以及把原生句柄递给需要的人。它是唯一知道自己跑在 Windows 上、句柄是 HWND 的地方。也是唯一允许用 ImGui 的地方——引擎层不认识 UI 这个东西。

这一层最容易踩的坑 ImGui 的 Vulkan backend 初始化时需要已经创建好的 instance、physicalDevice、device、queue。所以顺序必须是：先建 device，再 ImGui_ImplVulkan_Init。反过来不会报错，会在驱动里崩，栈还很浅，看起来像「Vulkan 装坏了」。
L2编排层：这一帧画什么
宿主编排契约后端驱动同步

RenderSystem::renderFrame() 是全场唯一一个「知道一帧长什么样」的函数。它不画，它排。

输入
一只手（device）+ 场景里的物体、相机、灯光。
决定
这帧切几个 pass（Shadow / Normal / Sky / Pick），每个 pass 的清屏色、渲染目标、管线、要画的物体清单；最后插一段 overlay。
输出
一串语义级意图：目标 + 管线 + 顶点流 + 索引流 + 纹理 + 一组矩阵。
这一层不懂
这些意图最后变成哪些 API 调用。它也不该懂——懂了就焊死了。

一帧的全部形状，去掉细节就这么点：

// 示意：形状对，签名以代码为准
if (!dev->beginFrame()) return;          // 没图像 → 整帧跳过
for (pass : passes) {
    cl = dev->createCommandList();          // 附加列表
    pass->record(cl);                       // 各 pass 自己录
}
overlayFn(cl);                              // ImGui 录进同一帧
dev->endFrame();                            // 提交
dev->present();                             // 呈现

八个词，就是一条帧。这里有两个细节值得停一下：

一、beginFrame() 返回 bool。 交换链正在重建、或者窗口最小化，这一帧根本没有可画的图像。返回 false 让上层直接跳过录制——少了这个 bool，你会在 acquire 失败之后继续录一堆没人执行的命令，然后在下一轮莫名其妙地崩。这是一个「用返回值表达状态」而不是「抛异常 / 断言」的选择，很工程。

二、endFrame() 只提交，present() 单独一个。 因为提交和呈现是两个不同的时刻，中间还夹着信号量。这跟 GL 用 SwapBuffers 一把做完不一样——两个后端要共用一套语义，就得按最严格的那个（Vulkan）来切。

怎么验证这一层没漏 在 RenderSystem.cpp 里搜 vk 和 gl，应该搜不到任何东西。搜得到，就说明编排层偷偷知道了后端是谁——这是分层的第一个裂缝。
L3契约层：把「意思」翻译成「ID 和参数」
宿主编排契约后端驱动同步

从这里开始，「一套接口支持两种后端」才成立。契约层只干两件事，别的都不干。

第一件事：把物体变成 ID。 上层说「我要一块 1MB 的数据存顶点」，契约层还一张 BufferHandle——一个 {id, gen} 的两字段结构。之后上层永远只说「用 3 号 buffer」，不会碰 VkBuffer。

第二件事：把「画」变成命令录制。 上层说 drawIndexed(...)，契约层的 IRHICommandList 就把它记进一个命令列表。注意是「记进」，不是「画掉」。这个区别就是 Vulkan 和 OpenGL 的全部差别。

输入
编排层给的语义：目标、管线、流、纹理、矩阵。
决定
句柄分配、代际校验、参数打包成 Desc、命令写进哪个列表。
输出
6 个句柄 + 8 个 Desc + 15 条录制方法。对上层来说，两个后端长得一模一样。
这一层不懂
谁真的在画。它只知道自己有两个子类要填。

这一层只有 12 个对象，但只有 2 个需要多态：IRHIDevice 和 IRHICommandList。剩下 6 个是纯数据句柄，8 个是创建时一次填好就再也不改的 Desc。

为什么句柄不做成 class 句柄没有行为，只有身份。一旦它变成有方法的对象，上层就会「顺手」调它——texture->lock()、buffer->upload()，抽象立刻漏。有行为的东西留在 device 上，句柄只负责「是谁」。这条写死在 RhiTypes.h 的文件头注释里。

另一条隐形的规则，必须靠人去记：录制顺序必须等于提交顺序。Vulkan 那边你录进 A、B 两个列表，提交时也按 A、B，那就是对的。GL 那边没有「提交」这个东西——createCommandList() 返回的就是主列表本身，调用即刻生效。所以多列表录制在 GL 上只能退化成串行，而且一旦你录的顺序和提交顺序不一致，画面会错，但不报错。docs/4-RHI接口契约.md 与 IRHIDevice.h 的 createCommandList 注释里，这两条都已经写进去了（硬约束一、二）。

L4后端层：同一句话，两种落法
宿主编排契约后端驱动同步

这一层是整套设计里唯一真正「两份代码」的地方，也是唯一该有 #ifdef 的地方。挑一个最普通的方法看，就能看出两个后端的性格差异。

看 bindTexture(slot, tex) 这一句：

Vulkan · VkCommandList
  1. 不立刻绑。把「set1 的第 slot 个 = 这张纹理的 descriptor set」记下来。
  2. 等到 draw 的时候，才一次性 vkCmdBindDescriptorSets。
  3. 如果连续 5 个 draw 的 set 组合完全相同，跳过重绑——省的是驱动层的工作。
OpenGL · GLCommandList
  1. 立刻绑：glActiveTexture + glBindTexture。
  2. 因为 GL 是全局状态机，「绑了就是绑了」，没有录制这回事。
  3. 所以必须配一套 GLStateSnapshot：进 pass 存状态，出 pass 恢复，否则上一个 pass 的设置会漏到下一个。

同一句调用，VK 那边是「攒着」，GL 那边是「立即 + 事后还原」。这不是实现风格问题，是两个 API 的模型不同，而契约层把这种不同吸收掉，所以上层写一遍就够。

动作Vulkan 后端OpenGL 后端
开始一帧等 fence、拿图像、重置 fence、uniform 环游标归零基本无事，清一下状态缓存
进入 pass开始一个 dynamic rendering，写清屏、写目标绑 FBO、设视口、清屏
绑纹理记进 set 数组，延迟到 draw立即 glBindTexture
绘制vkCmdDrawIndexedglDrawElements
结束一帧屏障 → 结束录制 → 提交 → 挂 fence无（命令早已执行）
呈现vkQueuePresentKHRSwapBuffers
这一层的验收标准 后端层允许出现 vk*、gl*、VkBuffer、GLuint。除此之外任何地方出现，都是漏。只允许一处运行期分支：RHIFactory::createDevice。别的地方写 if (backend == VK)，就是在把两套实现搅在一起。
L5驱动层：整个 Vulkan 其实就这十几个调用
宿主编排契约后端驱动同步

「跑通 Vulkan」听起来像三百件事。实际上一帧的调用链只有十几环，顺序固定。把下面这张表从上往下背下来，你就跑通了。

  1. vkWaitForFences等这个槽位上一帧真的干完。前提：fence 是「挂起」状态，所以必须先 reset 过
  2. vkAcquireNextImageKHR问交换链要一张可以画的图，同时 signal imageAvailable
  3. vkResetFences ← 必须在 acquire 成功之后acquire 失败时 early return，fence 不能已经被重置，否则下一帧会等一个永远不会 signal 的东西，直接卡死
  4. （无 API）环游标归零每帧槽位一条 uniform 环，游标回到 0 号偏移；不调 vkResetDescriptorPool，描述符创建期写一次后不再改
  5. vkBeginCommandBuffer × N每个附加列表 + 主列表各一个
  6. vkCmdBeginRenderingdynamic rendering：目标格式、清屏值都在这时候说
  7. vkCmdBindPipeline / vkCmdBindDescriptorSets / vkCmdBindVertexBuffers / vkCmdBindIndexBuffer四个绑定。描述符因为是动态偏移的，这里带 offset
  8. vkCmdDrawIndexed真正的绘制：indexCount、instanceCount、firstIndex、vertexOffset
  9. vkCmdEndRendering收一个 pass
  10. vkCmdPipelineBarrierCOLOR_ATTACHMENT_OUTPUT → PRESENT_SRC_KHR。dynamic rendering 不会替你写 finalLayout，漏了就是黑屏
  11. vkEndCommandBuffer结束录制
  12. vkQueueSubmit按「附加 → 主」顺序提交；等 imageAvailable，waitStage 用 COLOR_ATTACHMENT_OUTPUT（不是 TOP_OF_PIPE）；signal 这张图的 renderDone
  13. vkQueuePresentKHR等 renderDone，然后交给显示引擎
这一层，我们写不写代码 不写这一层。驱动 API 属于 SDK，不属于我们——我们的活是「按正确顺序调用它、把参数填对」。真正算我们自己写的只有三样：① 函数指针表（扩展函数比如 vkCmdBeginRenderingKHR，header 里只有声明，必须用 vkGetDeviceProcAddr 取地址，取不到就得当场报错）；② 着色器编译（GLSL 到 SPIR-V，构建期 glslangValidator）；③ 同步策略（什么时候等 fence、什么时候能删、删几帧）。

所以越往下，代码越少、责任越大：L5 近乎零行，L6（同步）才是真正费脑子的那层。

资源创建那一半（instance、物理设备、队列、swapchain、描述符布局、SPIR-V 管线、fence 和信号量）只在启动时跑一次，是另一条独立的路。日常跑帧，就是上面这十三步。

三个症状，九成出在这一层 启动就崩：几乎都是拿空指针去建资源，或者 validation layer 报了你没看。
全程黑屏：先查第 10 步的屏障有没有写；再查 viewport 的 y 轴——Vulkan 的 y 朝下，深度范围是 0 到 1，跟 GL 正好相反。
跑几十帧后卡死：先查第 3 步顺序，再查 waitStage 是不是 TOP_OF_PIPE。
L6同步与显存：这一层最不直观，也最容易出事
宿主编排契约后端驱动同步

这一层不画东西，只回答一个问题：这个资源现在还有人在用吗。 回答错了，画面会花、会崩，而且崩的位置跟你写错的地方没关系。

四个东西，各管一件事，不要混：

东西管什么不这么做会怎样
VkFence
每槽位一个		这个槽位的命令，GPU 干完没有还没干完就复用命令缓冲 → 内容和预期不符、随机崩
imageAvailable
每槽位一个		交换链给的图，可以开始画没有抢在呈现之前写 → 撕裂、闪烁
renderDone
每张图一个		这张图，我画完了没有present 读到没画完的图 → validation 报 VUID 00067；用一张图一个信号量就是为躲这个
延迟销毁队列
DeletionQueue		这个资源，真的没人用了吗CPU 侧 delete 立刻释放 → GPU 还在读，use-after-free

为什么销毁要等两帧。 你在第 N 帧决定「这张纹理不要了」。但 GPU 现在可能还在跑第 N-2 帧的命令，里面正读着它。所以 DeletionQueue::kLagFrames = 2：把释放动作排到两帧之后，而且必须挂在 fence 之后执行，顺序是「先 flush 队列，再 ++_frameCount」——反了就等于没等。

从 GL 带过来的习惯，在 VK 上是错的 在 GL 上 glDeleteTextures 之后句柄立刻失效，但驱动会自己把真实释放推迟到没人用为止——你随手删是对的。搬到 VK 上，vkDestroyImageView 立刻释放，GPU 还在用。而且它不一定当场崩，可能三帧之后花屏，可能换个场景才崩。这类 bug 的代价是按小时计的。

所以「Texture 能不能释放」的答案是：能，但不能当场释放。 契约层给你一个 destroyTexture，它做的只是把释放动作排进队列。上层觉得自己删干净了，实际上下层替你等了。

07回程：录完之后，怎么回到屏幕

前面六层是从上往下剥。但一帧真正的走向是「下 → 上 → 下 → 上」，四个转折。

① 往下
录制
语义变成参数，参数写进命令缓冲。这一步 CPU 说了算。
② 往上
提交
命令缓冲交给队列。从这一刻起，GPU 说了算。
③ 往下
等待
fence 和信号量在底层把两边的节奏对上。
④ 往上
呈现
图像交给显示引擎。像素出现。

一句话记住方向：往下是「决定」变成「参数」，往上是「参数」变成「像素」。 中间那两次转折，就是同步对象存在的原因——它们不是 Vulkan 的麻烦，是两个执行者（CPU 和 GPU）必须有的接头。

08纵向切片：一次 drawIndexed 穿过六层

全景是横着看，这一节竖着切一刀。同一次绘制，在每一层眼里分别长什么样、错了会怎样。

层它看到的它干的它错了会怎样
L1 宿主什么都看不到只知道「这帧画完了」，继续下一圈窗口不刷新、白屏或黑屏，但程序不崩
L2 编排drawIndexed(ibo, indexCount, pipeline, 三组矩阵)决定这个物体归哪个 pass，给什么管线少画、画错顺序、深度不对
L3 契约三个句柄 + 一堆参数校验代际、写进命令列表、记下 set 组合句柄 gen 不匹配 → 断言；用 0 号句柄 → 断言。这里出错通常是早于这一帧的
L4 VK 后端句柄对应的 VkPipeline、描述符数组draw 前补一次 vkCmdBindDescriptorSets（连续 5 个相同就跳过）set 布局和 pipelineLayout 不一致 → 校验层报错；没开校验就是黑屏
L5 驱动vkCmdDrawIndexed(ic, 1, first, 0, 0)照做indexCount 传成顶点数 → 越界读，读到的全是垃圾几何
L6 同步这条命令还挂在 GPU 上保证它用的 buffer、纹理、描述符池都还没被释放花屏、随机崩、崩在别的地方

这张表最有用的地方是最后一列：症状和层对得上，你就不用瞎猜。 画面全黑但程序活着，往下三层找；程序崩了但崩得毫无关系，往上两层找销毁。

09边界：这套结构现在做不到什么

结构本身是通的——分层干净、逃生舱没变主路径（全仓库只有 app/GlfwHost.cpp 用原生句柄，就为给 ImGui）。问题都在契约字段和容器语义上，不在骨架上。

级别问题为什么必须改
已关闭createCommandList() 泄列表destroyCommandList 已进接口：VK 端覆写、GL 端空实现。门禁里有 RHI_CHURN 一项盯着它
已关闭RenderPassDesc::framebufferId字段已删。契约层现在没有 GL 概念直通
已关闭AttachmentLayout 表达不了 MRT已改成 colorFormats[4] + colorCount，只实现 color[0]；colorCount>1 建管线时明确报错
已关闭kMaxTexSlots = 4 太少已改成 8；descriptor 上限还要按设备裁（桌面 32、某些 Intel / MoltenVK 只有 8）
已关闭句柄槽位不复用HandleTable 已有 _freeSlots，先出后进
已写录制顺序 = 提交顺序；多线程录制只对 VK 成立在 docs/4-RHI接口契约.md 与 IRHIDevice.h 里；GL 端 createCommandList() 返回主列表、立即执行，没有补救余地

还有三件「到那天一定会逼你改结构」的事，现在不用做，但心里要有数：bindless（句柄模型会从「一个资源一个 id」变成「一段 id」）、自动同步的 Render Graph（同步从手写变成编译出来）、真正的多线程录制（VK 可以，GL 物理上不行，这一条会永久留在契约上）。

10怎么自己验证这份文档说的对不对

不用信我，跑四个开关就够。顺序很重要，从最粗到最细。

开关做什么该看到什么
RHI_SMOKE=1只跑到能出图一帧内出图，能退出。这是在验 L1 到 L5 的接线
RHI_PROBE=1第 30 帧回读屏幕中心像素颜色不是纯黑/纯背景。这是在验 L5 的屏障和 viewport
RHI_DUMP=1导出 PPM能拿 Photoshop 打开，几何位置对。这是在验 L2 的编排
RHI_CHURN=N反复创建销毁 N 轮N 大也不崩、句柄数不涨。这是在验 L6 的延迟销毁

两个后端各跑一遍：RHI_BACKEND=opengl 和 RHI_BACKEND=vulkan，画面应该一样。不一样，就去看 L4 那张对照表里哪一行没对上。
