L2渲染系统：这一帧画什么

RenderSystem::renderFrame() 是唯一知道「一帧长什么样」的函数。它不画，它排。设备也在它手里。

输入
DeviceDesc + 场景、相机、灯光。
决定
几个 pass、各自的目标/管线/清屏色、物体清单、overlay。
输出
语义级意图：目标+管线+流+纹理+矩阵。
不懂
这些意图变成哪些 API 调用。
包含
  • RenderSystem、RenderContext、Scene、TextureMng、FontManager
  • IRenderPass + Shadow / Normal / Sky / Pick
  • Model/Mesh/MeshPass/AABB/Light/camera
  • BaseDraw/Line/Sky/Text/ImageRectangle
持有

  • m_rhiDevice：裸指针别名（可能借用）
  • 5 个 shared_ptr + RenderSettings
  • 十几个句柄：阴影 / 拾取 / 冒烟 / 四边形

  • app / imgui / GLFW（门禁强制）

一帧的形状8 行 
// 形状对，签名以代码为准
if (!dev->beginFrame()) return;      // 没图像 → 整帧跳过
for (pass : passes) { cl = dev->createCommandList(); pass->record(cl); }
overlayFn(cl);                            // ImGui 录进同一帧
dev->endFrame();                          // 提交
dev->present();                           // 呈现

beginFrame() 返回 bool：交换链重建或窗口最小化时没有可画的图，返回 false 让上层跳过录制。endFrame() 只提交，present() 单独一步：中间夹着信号量，按最严格的 Vulkan 切。

自查 在 RenderSystem.cpp 里搜 vk 和 gl，应该搜不到。搜得到，就是渲染系统偷偷知道了后端是谁。
L3RHI 抽象层：意思 → ID 和参数

只干两件事：把物体变成 ID，把「画」变成命令录制。是「记进」，不是「画掉」——这就是 VK 和 GL 的全部差别。

输入
目标、管线、流、纹理、矩阵。
决定
句柄分配、代际校验、参数打包、写进哪个列表。
输出
6 句柄 + 8 Desc + 15 方法，两个后端长得一样。
不懂
谁真的在画。
包含
  • RhiTypes.h：RhiHandle{id,gen} 派生 6 个 + 8 个 Desc
  • IRHIDevice、IRHICommandList
  • RHIFactory：全仓唯一运行期后端分支
  • HandleTable、DeletionQueue、FrameUniformRing
持有
  • 接口本身零状态：全纯虚 + 默认实现
  • HandleTable：_slots（值 + gen + alive）、_freeSlots
  • DeletionQueue：kLagFrames = 2 + 闭包
  • FrameUniformRing：一块显存 + 游标
不包含
  • Vk*/GLuint（例外：FrameUniformRing.h）
  • render / app / GLFW / imgui
  • 「第几帧、在哪个 pass」这类运行状态
两条靠人记的硬规则写不进类型里

一、录制顺序 = 提交顺序。VK 提交固定「附加列表（按创建顺序）→ 主列表」。GL 没有提交：createCommandList() 返回主列表、即刻执行，所以多列表在 GL 上只能退化成串行。

二、一条列表同一时刻只给一个线程。多线程并行录制只对 VK 成立。

两条都写进了 docs/4-RHI接口契约.md 与 IRHIDevice.h 的 createCommandList 注释。

为什么句柄不做成 class一条设计红线

句柄没有行为，只有身份。一旦它有方法，上层就会「顺手」调 texture->lock()、buffer->upload()，抽象立刻漏。有行为的留在 device 上，句柄只回答「是谁」。

代价：销毁必须走 destroy*，句柄不会自己死。destroy 把槽 gen+1（立刻失效），并把 GPU 删除排进队列。

L4RHI 实现：同一句话，两种落法

唯一真正「两份代码」的层，也是唯一该有 #ifdef 的地方。

包含 · VK
  • VkDevice（只编排）、VkDeviceInit（实例/设备/队列）
  • VkCaps、VkSwapchain、VkFrames
  • VkDescriptors、VkPipelines、VkShaderReflect
  • VkMemoryAllocator、VkCommandList、VkCommon
包含 · GL
  • GLDevice、GLCommandList、GLProgram
  • GL 侧不建上下文，只要求宿主已 current
不包含
  • render 层任何类型
  • GLFW、imgui
  • 例外一条：GLCommandList.cpp 依赖 DrawUniforms
同一句 bindTexture，两种落法模型差异
Vulkan
  1. 不立刻绑：记下「set1 第 slot 个 = 这张纹理的 set」
  2. draw 时才 vkCmdBindDescriptorSets
  3. 连续 5 个 draw 组合相同就跳过重绑
OpenGL
  1. 立刻 glActiveTexture + glBindTexture
  2. 全局状态机：绑了就是绑了，没有录制
  3. 必须配 GLStateSnapshot：进 pass 存、出 pass 还原

不是风格问题，是两个 API 的模型不同；契约层吸收掉，上层写一遍就够。

四个时刻：什么时候能删、什么时候能交同步纪律
要回答谁回答在哪
这批命令 GPU 跑完没fence，每槽一个VkFrames
这张图能交给显示引擎没renderDone，每图一个VkSwapchain
这个删除排到第几帧DeletionQueue + _frameCountDeletionQueue.h · VkDevice
帧内建的纹理本帧能采样吗layout 是否 UNDEFINEDVkDevice::textureSet
  1. beginFrame等本槽 fence → flush 到期删除 → 帧号 +1 → 描述符环归零
  2. createTexture帧内创建走 deferGpuWork，上传推到下一帧；本帧采样退白纹理
  3. destroy*句柄 gen+1 立刻失效，删除闭包入队，写「帧号 + 2」
  4. endFrame / present提交 → signal 该图 renderDone → 等它才交图

为什么两帧：你在第 N 帧删，GPU 可能还在跑 N-2 帧的命令。所以 kLagFrames = 2，且必须挂在 fence 之后——先 flush 再 ++_frameCount，反了等于没等。

从 GL 带来的习惯，在 VK 上是错的 GL 上 glDeleteTextures 后驱动自己会推迟释放，随手删是对的；VK 上 vkDestroyImageView 立刻释放，而 GPU 还在用——而且不一定当场崩，可能三帧后花屏。
验收标准 这一层允许出现 vk*、gl*、VkBuffer、GLuint，别处出现就是漏。运行期分支只允许一处：RHIFactory::createDevice。

这些真实对象的名字不出现在 L4 的对外身份上——它们在各模块内部，外面只看见一个 IRHIDevice*。

⑥ 墙外：把 handle 变成 GPU 上下文我们不看它

驱动只做一件我们关心的事：把 instance + device 变成真的 GPU 上下文（ICD、队列、显存）。我们不读它，只在失败时收到 VkResult。

斜率：L1 给 1 张 Desc → L2 给 8 种 Desc → L3 一个字段不改 → L4 摊成几十个结构体字段 → 墙外只还一个结果码。越往下参数越多、人越少。

创建顺序三条硬的 一、窗口 → surface → 物理设备 → device → swapchain（挑卡要问 surface 支不支持呈现）。
二、descriptorSetLayout → pipelineLayout → pipeline。
三、device → ImGui 的 descriptor pool。

还有一类创建是每帧的：createCommandList 的附加列表、上传用的 staging buffer、deferGpuWork 回调。寿命一到两帧。

window：一个结构体，干了两种完全不同的活NativeWindow

字段名叫 window，其实是两套东西拼在一起：前三样是给 Vulkan 造 surface 用的坐标，后两样是给 OpenGL 换帧用的钩子。两个后端各取所需，互相不认识。

window.typeVulkan 加的平台扩展填进哪个结构体
Win32VK_KHR_win32_surfaceVkWin32SurfaceCreateInfoKHR：hwnd = (HWND)handle，hinstance 自己取
XlibVK_KHR_xlib_surfaceVkXlibSurfaceCreateInfoKHR：dpy = (Display*)display，window = (Window)handle
XcbVK_KHR_xcb_surfaceVkXcbSurfaceCreateInfoKHR：connection = display，window 从 handle 转成 xcb_window_t
WaylandVK_KHR_wayland_surfaceVkWaylandSurfaceCreateInfoKHR：display + surface = (wl_surface*)handle
MetalLayerVK_EXT_metal_surfaceVkMetalSurfaceCreateInfoEXT：pLayer = handle
Cocoa同上，但不能自建handle 是 NSView，要 NSView → CAMetalLayer 的转换，引擎不碰 ObjC++ → 必须走宿主的 createSurface 回调

所以 GlfwHost::buildDeviceDesc 在 macOS 下只填 type=Cocoa 和一个 createSurface lambda，里面调 glfwCreateWindowSurface；Windows 下连回调都不用给，引擎自己 vkCreateWin32SurfaceKHR。

它的一生（VK 只用到第 3 步，GL 只用到第 6 步）：

  1. 搭窗口GL 模式：glfwWindowHint 3.3 core + GLFW_SRGB_CAPABLE → glfwCreateWindow → makeContextCurrent → gladLoadGLLoader。VK 模式：只加一个 GLFW_NO_API，根本没有 GL 上下文，窗口退化成一块能往上贴图的 OS 表面
  2. 填表buildDeviceDesc 只搬四样：type（编译期平台宏）、handle（(void*)_window）、swapBuffers=swapAdapter、swapUser=_window。此刻它还是原样的 OS 句柄，没被翻译
  3. 变成 surface仅 VK。按 type 挑平台扩展 + 挑一个 vkCreate*SurfaceKHR → surface 就是 window 在 Vulkan 世界里的替身，造出来以后，下面所有调用都不再碰 window
  4. 挑卡vkGetPhysicalDeviceSurfaceSupportKHR：队列族既要 GRAPHICS 又要能呈现给这块 surface。没有 surface 就挑不出卡——这就是为什么 surface 必须早于物理设备
  5. 定交换链vkGetPhysicalDeviceSurfaceCapabilitiesKHR 拿 currentExtent 和 currentTransform，SurfaceFormatsKHR 挑 B8G8R8A8_SRGB，PresentModesKHR 挑 FIFO。尺寸、朝向、格式、呈现模式全是从 surface 问出来的，不是从窗口
  6. 出图交图VK：每帧 vkQueuePresentKHR 仍然带着这个 surface。GL：present() 调 swapBuffers(swapUser) → glfwSwapBuffers，把上下文的后备缓冲推上屏
  7. 收尾RHI 自建的 surface 在设备析构时 vkDestroySurfaceKHR，必须早于 instance；窗口归宿主，必须晚于 device 销毁（shutdown 在 glfwTerminate 之前）
一句话记住两边相反 VK：window 只活到 surface 造出来，之后是 surface 在干活。GL：window 活到最后一次 present —— 因为 GL 的默认帧缓冲是上下文的附属物，不是 RHI 创建的对象，只能由宿主那一下 swapBuffers 交出去。
不填的后果不一样 GL：构造时就检查 window.valid() 和 swapBuffers，缺一个立刻报 invalid or missing swapBuffers callback，工厂返回空。
VK：platformInstanceExtensions 对 type=None 返回 false，报 no platform instance extension for window type；type 对了但平台宏没编进去，也会落到“没有平台 surface 路径”那个分支。
为什么 GL 要 swapBuffers 而 VK 不要：VK 交图是 vkQueuePresentKHR，驱动知道 image 该给谁；GL 只知道“当前 framebuffer”，推上屏得靠宿主，因为 GL 的默认帧缓冲是上下文的一部分，不是 RHI 创建的对象。
渲染到窗口：没有“把画面贴到窗口”这个操作

两边都只做一件事：把画面画进一块「能被合成器取走」的缓冲，然后交给系统。区别只在这块缓冲归谁、叫什么名字。

OpenGL：0 号帧缓冲
  1. beginRenderPass 里 renderTarget 无效 → glBindFramebuffer(GL_FRAMEBUFFER, 0)。这一句就是“绑到窗口”
  2. 0 号 FBO 是上下文创建时驱动生成的，背后就是窗口的 drawable。窗口不是用句柄绑的，是用“当前上下文”绑的——谁 current 就画到谁
  3. 视口用 _device->framebufferSize()（像素值），不回查窗口系统
  4. 交图：present() → swapBuffers(swapUser) → glfwSwapBuffers，驱动把后备缓冲 flip 给合成器
Vulkan：swapchain 第 i 张图
  1. 窗口在建 surface 那天就绑完了，此后每帧不再出现窗口参数
  2. beginFrame → vkAcquireNextImageKHR，拿到的 _imageIndex 就是本帧要画的那张
  3. vkCmdBeginRendering 的 imageView = currentColorView()；MSAA 时渲进 msaaColorView()、再 resolve 回它
  4. 收尾 endRenderPass 把这张图转成 PRESENT_SRC_KHR，present() 用同一 index + surface 调 vkQueuePresentKHR

四个最常见的坑 GL：pass 结束时没把 FBO 绑回 0，后面的 overlay 就画进了离屏 RT——屏幕黑的，但 RT 里有内容。
GL：多窗口时 glfwMakeContextCurrent 没切对，画到另一个看不见的窗口里，不报错。
VK：present 用了上一帧的 _imageIndex，校验层报 VUID；resize 后不重建 swapchain，就按旧 extent 出图，黑边或拉伸。
两边：sRGB 的编码端不是一个地方——GL 靠 GL_FRAMEBUFFER_SRGB 开关 + 默认帧缓冲的 encoding 探测，VK 靠 swapchain 格式本身是 B8G8R8A8_SRGB，写进去就编码。
present：GL 的最后一步根本不在 GL 里

三段调用，第三段是平台 API，不是 gl* 函数：

1
GLDevice::present()：if (_window.swapBuffers) _window.swapBuffers(_window.swapUser); —— 就两行，RHI 到这里交棒
2
GlfwHost::swapAdapter(void* user)：glfwSwapBuffers((GLFWwindow*)user)。为什么绕一个裸函数指针：rhi/gl 不许 include GLFW
3
glfwSwapBuffers 的平台实现：Win32 SwapBuffers(hdc) / X11 glXSwapBuffers / Wayland eglSwapBuffers / macOS [NSOpenGLContext flushBuffer]。没有一个是 OpenGL 规范里的函数，全是窗口系统的

这就是 RHI 做不了 present 的原因：GL 规范里没有“把画面上屏”这个 API，只有“当前上下文 + 默认帧缓冲”。上屏属于平台层，必须问宿主。

底下是什么：双缓冲与交换flip 
           ┌──────────────────────────────┐
  屏幕  ◀── │ front buffer（合成器读的是它）│
           └──────────────────────────────┘
                   ▲ swapBuffers 交换这两块
           ┌──────────────────────────────┐
           │ back  buffer（glDraw* 只写它） │
           └──────────────────────────────┘

上下文一建好就有两块缓冲。所有绘制只进 back，front 是别人正在看的。交换那一下（flip，或 copy+blit，看驱动/合成器）把 back 交出去。于是“画到哪个窗口”这件事的答案就是：front 是哪块，窗口就显示哪块。

GL 里永远只有一张 back buffer 在画 —— 你无法“指定第几张图”，那是 VK 才有的事。这也是两边架构差异的源头。

vsync 就挂在交换上：glfwSwapInterval(1) = 驱动把交换推迟到下一次垂直消隐。本仓库不是建窗时写死，而是由 DebugPanel::draw 里 glfwSwapInterval(settings.vsync ? 1 : 0) 实时切。

所以 GL 的限帧发生在 present，不在绘制：swapBuffers 在队列满或 vsync 未到时通常直接阻塞。你拿不到“GPU 落后几帧”的任何信息——驱动内部有私有队列，帧延迟是隐式的。

共同点：最终都由系统的 presentation engine 决定什么时候上屏。区别是 GL 把它藏起来，VK 把它摊开成你可以排队的 API。

这个差异直接决定了架构，五条：

  1. present() 在 GL 是转发、在 VK 是真动作所以接口签名只能是无参无返回值的“通知”，不能表达“排第几帧”
  2. GL 没有 acquire → 主 pass 的目标用“无效句柄”当哨兵beginRenderPass 里那句 desc.renderTarget.valid() 就是这两条路的分叉点；VK 内部换成 currentColorView()
  3. GL 没有 swapchain → resize 由窗口系统自动重建 drawableVK 必须重建 swapchain，所以 beginFrame() 要返回 bool 让上层跳过这一帧
  4. GL 的限帧在 present，VK 的在 acquire/fence压测对比时两边帧率行为天然不同，RHI_CHURN 的数字不能直接互比
  5. GL 必须单线程 current，VK 可以并行录制这就是“多列表录制顺序规则只对 VK 成立”的根
四个必须在 present 之前做完的事 一、overlay（ImGui）必须在 present 之前画进 0 号 FBO；放到后面，那帧就丢了。
二、回读（RHI_PROBE/RHI_DUMP）必须在 present 之前。交换之后 back buffer 已变成“上一帧的 front”，glReadPixels 读到的是未定义内容——本仓库放在 GLDevice::endFrame()，顺序是对的。
三、vsync=false 时 swapBuffers 不阻塞，不限帧就是几千 FPS；RHI_EXIT_AFTER 这类按帧计数的测试会在几十毫秒内跑完，别以为是引擎快了。
四、glfwSwapBuffers 会顺手把该窗口的上下文设为 current，所以多窗口时 present 不会串窗口；但绘制仍依赖 createWindow 里那次 glfwMakeContextCurrent。
width / height：名字是“帧缓冲像素”，不是窗口尺寸

DPI 缩放下两者不等。L1 两个都取了：glfwGetFramebufferSize 进 DeviceDesc，glfwGetWindowSize 进 InitDesc.windowWidth/Height——后者只给拾取做坐标换算（鼠标是逻辑坐标，图是像素）。

后端用它干什么填 0 会怎样
VKvkCreateSwapchainKHR 的 extent：caps.currentExtent 是 UINT32_MAX（组合器说“你自己定”）时才回退到它；onResize 重建 swapchain 时也用它extent 为 0 → 创建失败
GL存 _size；framebufferSize() 返回它；readback 与 RT 尺寸跟它走RT 创建直接报 width==0 || height==0

注意 VK 的 extent 优先用 caps，你填的值只是兜底——这是 Vulkan 的规矩，不是引擎的选择。onResize 只是更新这个字段，重建发生在下一帧 beginFrame。

msaaSamples：VK 里是指令，GL 里只是声明
Vulkan：说了算
  1. 传给 VkSwapchain::create，跟着建 MSAA 彩图 + resolve 附件
  2. 所有画到主帧缓冲的管线必须声明同样的 samples，否则该 pass 报错并跳过
  3. 改它 → 交换链对象整套重建
OpenGL：说了不算
  1. GL 的默认帧缓冲采样数在上下文创建那一刻就定了（glfwWindowHint(GLFW_SAMPLES)）
  2. RHI 改不了，只能 glGetIntegerv(GL_SAMPLES) 读回来比对
  3. 不一致 → 打 ERROR，故意不静默按实际值出图

所以 GL 下想真开 MSAA 得去改宿主建窗参数，改 DeviceDesc 只会得到一条错误日志。这个“不静默”是刻意的：静默了你会以为设置生效了。

enableValidation：只在 VK 有意义

VK 拿它当 wantValidation 的初值：真 → 尝试启用 VK_LAYER_KHRONOS_validation（可用 RHI_VK_VALIDATION 覆盖）；假 → 明确不启用。GL 完全不读，GL 没有校验层，调试手段只有 glGetError 和 KHR_debug。

默认值是 true，所以 demo 默认就带校验层跑。它属于“构建允许就开”的字段，不是性能开关。

三个逃生口：宿主接管 Vulkan 的时机instanceExtensions / createSurface / externalSurface

公共头里不许出现 Vk 类型（RhiTypes.h 不 include vulkan.h），所以这三个入口都用 uint64 传句柄，宿主自己 reinterpret_cast。三个有优先级：

  1. externalSurface != 0直接用，_surfaceOwned = false，析构时不动它 → 宿主负责销毁
  2. createSurface 有值拿 VkInstance 回调宿主；返回非 0 则 _surfaceOwned = true，RHI 销毁
  3. 都没给按 window.type 自建，RHI 销毁

instanceExtensions 同样优先：非空就一个不加地照用，空才按 window.type 推导。想加 VK_EXT_debug_utils 之类又不想改引擎，就从这里塞。

为什么非要留这个口 macOS 的 NSView → CAMetalLayer 要 ObjC++，GLFW 内部已经做过这件事；引擎一旦自己去碰，就得为“不碰 GLFW”这条规矩开例外。逃生口把这段搬回宿主，代价只是多一个 std::function 字段。

这条链上唯一不能做的事 L1 填 → L2 原样塞进 InitDesc → L3 一个字段不改 → L4 逐字段消费。L3 的职责里包含“不改”：工厂或契约层一旦替宿主补默认值、纠正参数，你就再也无法从“L1 填了什么”推出最终行为。要补默认值，就补在 DeviceDesc 的成员初始化上（那里本来就是默认值）。
08墙外：一帧的十几个调用
这一节不是一层 零文件、零 include 边，只有 <vulkan/vulkan.h> 和 <glad/glad.h> 被 rhi/vk、rhi/gl 引进来。我们不写它，只排顺序、填参数。
  1. vkWaitForFences等本槽上一帧干完（fence 必须先 reset 过）
  2. vkAcquireNextImageKHR要一张能画的图，signal imageAvailable
  3. vkResetFences必须在 acquire 成功之后：失败就 early return，否则下一帧等一个永不 signal 的东西，卡死
  4. 环游标归零不调 vkResetDescriptorPool：描述符创建期写一次就不改
  5. vkBeginCommandBuffer × N每个附加列表 + 主列表
  6. vkCmdBeginRenderingdynamic rendering：目标格式、清屏值在这时说
  7. vkCmdBindPipeline / BindDescriptorSets / BindVertexBuffers / BindIndexBuffer描述符是动态偏移，这里带 offset
  8. vkCmdDrawIndexedindexCount、instanceCount、firstIndex、vertexOffset
  9. vkCmdEndRendering
  10. vkCmdPipelineBarrierCOLOR_ATTACHMENT_OUTPUT → PRESENT_SRC_KHR。dynamic rendering 不替你写 finalLayout，漏了就是黑屏
  11. vkEndCommandBuffer
  12. vkQueueSubmit按「附加 → 主」提交；等 imageAvailable，waitStage 用 COLOR_ATTACHMENT_OUTPUT；signal 该图 renderDone
  13. vkQueuePresentKHR等 renderDone 再交给显示引擎

真正算我们写的只有三样：① 函数指针表（vkGetDeviceProcAddr 取 vkCmdBeginRenderingKHR，取不到当场报错）；② 着色器（GL 侧 GLProgram，VK 侧构建期 glslangValidator）；③ 同步策略。

三个症状，九成在墙这边 启动就崩：空指针建资源，或验证层报错你没看。
全程黑屏：先查第 10 步屏障；再查 viewport 的 y 轴（VK 朝下、深度 0..1，跟 GL 相反）。
几十帧后卡死：先查第 3 步顺序，再查 waitStage 是不是 TOP_OF_PIPE。
